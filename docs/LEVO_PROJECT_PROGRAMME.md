## B. Architecture

One sentence: **a merchant describes a product once (a blueprint), a customer's choices become one immutable value (a configuration) that every existing door carries by id, the Levo Project is a family of ordinary requests around one page, production is an overlay that reads orders and never writes them, and every dinar moves through the existing escrow, now sliceable into parts.**

**The surface compiler** (`surface.ts`) turns any blueprint into ≤ 4 tiles + 1 door: slot 1 = the main content (name > photo > logo > text > QR), slot 2 = Look (when any region offers ≥ 2 colours or themes apply), slot 3 = Size (when the size axis has ≥ 2 values), empty slots promoted from QR › add-ons, More only when something is left; the door is chosen by the engine (blocked → disabled with the fix chip; review → «Request printing» or «Ask the shop»; ready/adjusted → «Add to cart» when the blueprint sells by cart). ### B.2 Live 3D: regions and anchors

**Primary — named regions on the existing LVM1 path** (media3d survey (A), recommended primary):

1. **Ingest** (merchant, C1): `parseModelParts` beside `analyseModel`/`viewerMesh`, which stay byte-identical: 3MF `<components>` with composed transforms and per-object names and colours (today a Bambu/Prusa assembly measures `NO_GEOMETRY`; the fix is `parseModelParts`' only — `analyseModel` and `parse3mf`, which reads the root model part alone (`modelGeometry.ts:679-721`), keep request files and quotes byte-identical); OBJ `o/g/usemtl`; glTF nodes with transforms and names; or up to 12 STL files placed by their stored bboxes. fflate stays inside its allow-listed file (`tests/store-isolation.test.ts`); modelGeometry's bounded ZIP reader is exported instead.
2. **Mesh**: LVM1 byte-for-byte, then the trailer `'LVR1' | u16 parts | u16 0 | parts × (u32 start, u32 count)`. Parts are contiguous; names never enter the file (merchant-only in `product_blueprints.parts`); today's `parseLvm` ignores trailing bytes (`ModelViewer.tsx:209-217`); `coarsePreviewMesh` is not used for blueprints.
3. **Render**: a per-vertex Uint8 part attribute → region index → `uniform vec3 uRegion[16]` indexed in the **vertex** shader (GLSL ES 1.00 guarantees dynamic uniform indexing only there); recolour = one uniform write and one draw call; finishes as sheen / emissive / roughness; accessory marker parts visible only while their slot is filled, and where the merchant modelled none, a simplified marker drawn at the slot's declared anchor (a glow for an LED, a ring for a magnet, a badge for a motor).
4. **Decals**: ≤ 4 areas in one 1024² canvas atlas (ogl `Texture`); projective coordinates, the region mask and a facing test computed in the vertex shader (≤ 7 of WebGL1's 8 varyings); text drawn with `fillText` in the self-hosted Cairo after `document.fonts.load`, so browser shaping and bidi give real Arabic and Sorani (the Worker has no shaper); QR modules from `qrEncode`; logos posterised; lithophane previewed as a back-lit grayscale plate.
5. **Picking**: our own Möller–Trumbore test over the Float32Array → triangle → part (binary search over the LVR1 ranges) → region → its editor; every tap has a list twin.
6. **Delivery**: `merchants/<uid>/public/bp/<blueprintId>-r<rev>-<hash12>.lvm.gz` stored as `application/gzip` through `CompressionStream`, served by `/files` (public, immutable, edge-cached, Range, 0 D1), inflated with `DecompressionStream`. No new mesh route (`anonymousCached` reads `built.text()`, `worker/lib/edgePolicy.ts:211`, so no binary goes through it).

**Fallback — the look card** (media3d survey (C), in its still-plus-ID-map flavour): a public poster (≤ 400 KB, the store layout's poster cap) + an RLE region-id map at 256² (≤ 8 KB) + area quads + the camera, captured by the builder at publish (a neutral render and a flat ID pass read with `readPixels`). Any configuration renders in 2D: pixel = poster luminance × region colour, each area's artwork warped into its quad. It serves no-WebGL and lost contexts, browsers without `DecompressionStream` (iOS < 16.4), Save-Data (until the customer taps «Show the live preview»), cart lines, cards, My Designs rows and the merchant's card — no WebGL context per card, deterministic screenshots for Playwright. A photo-only blueprint (§0 row 39) uses the same renderer with the merchant's photo for the chosen value in place of the captured render (no region map: its colours are the product's own colour values, each with its photo). Not adopted: the client software rasteriser (measured 20 ms per 512² frame at 20k triangles, media3d) and server-side glyph extrusion (no Arabic shaper); raised production geometry is B′ in C15.

**State invariants** (named tests):
- **L1 Approval lock.** `lock(order)` = the latest non-withdrawn workshop version with a binding approval, else the acceptance snapshot; `production_hash` = sha256 of {request revision + hash, offer revision + option, locked version hash, approved change ids}, copied onto QC rows, serials, handoffs and evidence.
- **L2 Start.** The first version a workshop sends on a funded order starts the work through the start route's own fenced statements; design work can no longer be undone by a one-tap refunding cancel.
- **L3 Delivery.** Refused while the latest workshop version waits for a binding decision, while a change is pending (C6), or while terms that require approval have no approved version — one exported delivered statement builder; a pre-check gives the exact code (`VERSION_AWAITS_APPROVAL`, `CHANGE_ORDER_PENDING`).
- **L4 Versions.** Content immutable (trigger); withdrawn once, before any binding decision; approvals append-only (trigger); one binding decision per version (partial unique index); a customer's own revision copies the revision row's hash when it becomes version 1 (revision rows are rewritten in place until priced).
- **L5 Change orders.** Figures immutable; one pending per order; decided once; voided by dispute or cancel in the same batch (C6).

- **L7 Access.** `projectAccess()` derived per call: owner · stage merchant (engaged or direct merchant of THAT stage) · member viewer / commenter / approver · eligible (pre-order notes only) · null → 404 `PROJECT_NOT_FOUND`. Members never receive money, contact snapshots, chat or escrow; they read request and version files as **preview-only** readers — `requestFilePolicy.ts` gains the reader class `member` (the 3D preview and pictures, never original bytes) behind the request file door (`marketplace.ts:613`) and the viewer grants; a designer never sees the print stage's money or thread and vice versa; a block either way → 404.
- **L8 Invites.** A 32-byte token in the URL fragment (never logged, never a Referer), stored as sha256, 7 days, bound to one account, ≤ 10 live members; every bad case → `INVITE_INVALID`.
- **L9 Revision budget.** Included (terms) + purchased (approved `revision` changes) − used (binding changes-requested decisions); notes and pins never count; workshop versions never refused; the words of a decision are Phase 5's `modification_request` row, and a bare `modification_request` on an order with versions is refused `USE_VERSION_DECISION` (§0 row 15), so one customer act writes one approval and one timeline row and the budget cannot be bypassed.

### B.6 Money on the existing escrow

Nothing new holds, moves or records money: the wallet hold, the escrow with its append-only events and the append-only merchant ledger stay the only three money objects (`sale_royalties`, C16b, is an index over ledger `event_key`s with no balance, not a fourth). **Money rules** (each a named node:test case, written red before its feature):
- **M1** One escrow per order. A plan escrow's parent row has `hold_id` NULL, so the settlement builders refuse it (`escrowOps.ts:552,689`); its gross, fee and receivable equal the sum of its step parts, fenced in the acceptance batch. **A part hold is a claimed hold**: the legacy paths do NOT refuse it on their own — the stranded-hold sweep (`communityRequests.ts:800-817`), the accept route's «did it land?» (`marketplace.ts:2454-2462`), `releaseEscrowReservation`'s claimed test (`escrowOps.ts:354-381`) and the wallet's held dinars (`walletOps.ts:747`) read only `community_escrows.hold_id`, so the sweep would release every live part hold after `STRANDED_AFTER_MINUTES` and a lost accept response would release a committed plan's holds. C5 extends each with `OR EXISTS (SELECT 1 FROM community_escrow_parts p WHERE p.hold_id = <hold>)` (the held dinars read the part's gross), red tests first.
- **M2** One hold per part; a plan's cents computed once (0108's «at most one cent per order»); a wallet holding exactly the plan total accepts.
- **M3** Money leaves a part only inside `settleCommunityOrder`, in one batch whose part flip requires: the part still held; the parent held (`disputed` for an admin only); the order in the expected state; the paying customer's binding approval of the current version for that step; for a non-admin, the merchant not suspended (DECISIONS row 137).
- **M4** Credit only where the debit posted (`FUNDED_BY_HOLD` on every merchant credit and customer deposit); each hold committed at most once; refunding an unreleased part releases its hold. Every per-hold key is part-scoped — the ledger's `escrow:<escrowId>:<partId>:<stage>:<line>`, the refund transaction `wtx_escrow_refund_<partId>`, the rate read off the part's own `held` event (`community_escrow_events.part_id`) — while a single-hold escrow keeps today's keys byte for byte (golden), so a second part never aborts on the UNIQUE `event_key` (`0121:122`) and a change part held at a new rate settles at its own rate.
- **M5** Paid parts are final (no escrow claw-back path exists); a dispute freezes the parts still held and decides only them.
- **M6** Commission: one split at acceptance sliced across the steps (Σ = F exactly); change parts at the order's rate with no minimum; partial outcomes F5 (row 137) on the total kept, less what earlier parts charged, never negative; never refunded on an escrow.
- **M7** The delivery step carries the whole delivery fee and ≥ 30 % of the item price.
- **M8** Order terms frozen: price, fee, receivable, commission rate and the money keys of `offer_snapshot` — `price_iqd`, `delivery_fee_iqd`, `total_iqd`, `quantity` (`marketplace.ts:2421-2424`) plus C6's option key and plan totals, the keys no redaction may touch (D27) — cannot change after insert (trigger; a 0134-style redaction of request/contact snapshots, or of any other snapshot key, still passes).
- **M9** One pending change per order; delivery refused while one is pending; a dispute or cancel voids it in the same batch.
- **M10** A royalty never changes the customer's total, never exceeds the share it is carved from, is never a negative line in a seller's *available* bucket, and follows the money (paid when available, clawed back when taken back).
- **M11** Merchant-private money (cost, royalty rule, partner price, net) lives only in merchant-only tables and payloads; `community_orders` gains no cost/margin/royalty/profit/partner column; nothing of it enters `pricing_snapshot` or `offer_snapshot`.
- **M12** Caps: ≤ 4 step parts and ≤ 8 parts per escrow; ≤ 100 group entries (200 after a measured batch test).
- **M13** A merchant act alone never pays; an invited approver never pays; no automatic approval after silence (the workshop may open a dispute instead).
- **M14** The client sends ids and echo-only `expected_*` figures; a mismatch is a refusal, never a charge; never a price, margin, royalty, payee, `customer_id` or `merchant_id`.
- **M15** Who may move money: the payer's own routes; merchant routes behind `requireStoreOwner` (never P10 staff access); the system sweeps; admin routes behind `requireFinancialScope`. Every route is classified *moves / shows / none* (`tests/moneyRouteClass.test.ts`).
- **M16** One winner per compete group (a database trigger whose message contains «constraint», so the accept route's existing failure branch releases the losing hold — `worker/lib/walletOps.ts:448` `isConstraintAbort`); a partner job's money is never linked to the end customer's escrow.
- **M17** Parts use the existing event kinds: `community_escrow_events.kind` is a closed CHECK (`0031:174`), so a part writes `held` / `release` / `refund` with `part_id` set, and a credit is not an event but a smaller release plus a refund at settlement. Named tests (C5, red first): a plan accept whose response is lost releases no part hold; the sweep after `STRANDED_AFTER_MINUTES` leaves every part hold active; two parts of one escrow release without a UNIQUE abort; a change part held at a new rate settles at its own rate; the wallet's `iqd_held` equals the parts' gross.
