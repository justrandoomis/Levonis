## الملخّص التنفيذي (بالعربية)

نحوّل المنصّة تدريجيًا من Worker واحد إلى مجموعة Workers مستقلة على Cloudflare، لكلٍّ منها كودها وإعداد wrangler الخاص وأسرارها وصلاحياتها وجداولها وعقدها المعلن، خلف **بوابة API عامّة واحدة** تتولّى التحقّق من الجلسة، والتوجيه، وحدّ الطلبات، وفحص المدخلات، والتخزين المؤقّت الآمن، وTurnstile عند الحاجة. التواصل الداخلي يمرّ عبر Service Bindings فقط؛ لا خدمة تقرأ أو تكتب جدول خدمة أخرى، ويُنفَّذ ذلك باختبار في `npm run check` وقائمة تسامح للنواة القديمة لا تكبر أبدًا.

القاعدة الحاكمة: **نستخرج العقد قبل الكود، والكود قبل البيانات.** ما يُكتب اليوم في دفعة D1 واحدة (الشراء، المحفظة+النقاط، السعر+المخزون على نفس الصفوف) يبقى في وحدة نشر واحدة لكن كحِزم منفصلة بعقود منفصلة ونقاط دخول مسمّاة، فيصبح فصلها لاحقًا تغيير إعداد لا إعادة كتابة. الطلبات تتحوّل إلى Saga تُبنى وتُختبر داخل النواة أولًا خلف علم تشغيل، ثم تنتقل إلى Worker التجارة.

المال: `wallet_transactions` يبقى دفتر اليومية بدلالته الحالية؛ كل أمر مالي يحمل مفتاح تكرار إلزاميًا؛ التثبيت-مع-الخصم عملية ذرّية واحدة تُغلق الثغرة العليا في التقييم؛ الأرصدة تُحسب بالمجموع على D1 اليوم، وتصبح صفًّا مقفولًا بـ`FOR UPDATE` على PostgreSQL عبر Hyperdrive عند توفّره. سجلّ تدقيق غير قابل للتعديل (سلسلة تجزئة) يستهلك أحداث كل عملية حسّاسة.

الأحداث موحّدة الغلاف (event_id, event_type, version, created_at, source_service, correlation_id, actor_id) عبر صندوق صادر في مخزن كل منتِج، وموزّع عبر Bindings اليوم وQueues لاحقًا بتبديل إعداد. Ads وAnalytics وAudit وNotifications وSearch وRisk خدمات حقيقية بقواعد D1 خاصّة منذ البداية، بمحوّلات (adapters) لكل مزوّد خارجي.

لا يُحذف مسار ولا جدول ولا مهمّة؛ كل تغيير على البنية الحيّة (المسارات، الأسرار، الربط) بوابة يوافق عليها المالك، والتراجع عن كل شريحة معرَّف مسبقًا.

## 0. The rules that fixed this design

1. **Contract before code, code before data.** A domain's RPC + event contract is fixed first while the code still runs where its writes are atomic; the code moves to its own Worker only when every caller uses the contract and every cross-domain batch has a saga; data moves only after the code has its own Worker — and only with a separate owner approval (constraint 4).
2. **Merge a deployable only where a single D1 batch is the only correctness mechanism today** (assessment §2.2 B1–B16). Even then the deployable hosts **separate packages with separate contracts and separate named entrypoints**, so the split is a wrangler change plus a table move, never a code split.
3. **The gateway is the strangler.** It routes a prefix (and host class) to the owning Worker; the legacy core (`worker/`, live as `levonis-staging`) serves everything not yet moved. Rollback of any extraction slice is a routing flip.
4. **Dark first.** Every new Worker exists as a `-dark` deployment on a full preview stack before anything live changes; the live zone changes only at owner gates (`02-MIGRATION-PLAN.md`).
5. **Adapters, not rewrites.** Queues, Durable Objects, Workflows, KV, Hyperdrive, the `ratelimits` binding, Analytics Engine and every external provider sit behind an interface whose D1/cron/in-memory implementation runs today; provisioning them later is a config switch.
6. **Nothing is deleted.** Every mounted path, table, column, cron step and row keeps working; retirements are 410 shims and only with an owner decision.

### 2.3 The interim rule while services share one D1 (ADR-003)

1. **Ownership manifest per service.** `services/<name>/OWNERSHIP.json` (new) lists the tables the service may name in SQL (`owns`, `reads`). `packages/platform-kit/src/db.ts` `ownedDb(env.DB, manifest, mode)` wraps `prepare()` and refuses any statement naming a table outside the manifest (regex over `FROM|JOIN|INTO|UPDATE|DELETE FROM <name>`); `mode:'throw'` in dark, `mode:'log'` for the first production release of each service, then `throw`.
2. **Static lint.** `tests/serviceBoundaries.test.ts` (new, part of `npm run check`) scans every `.ts` under `services/<name>/src` for SQL literals and asserts the tables are in the manifest; asserts no `services/<a>/src` file imports from `services/<b>/src` or `worker/` — in particular not `worker/lib/ratelimit`, `worker/lib/audit`, `worker/lib/session` (only from `packages/*`, plus the one intra-deployable exception of ADR-004: `services/<deployable>/src/<sibling>/statements.ts`); asserts no bare `fetch(` outside the platform kit. ESLint `no-restricted-imports` mirrors the import rule per directory. **Why this matters for "files move verbatim":** every Phase-4 route file calls `rateLimit()` (`farm` 2, `uploads` 1, `invoices` 2, `kyc` 4, `policies` 2, `chats` 2, `support` 3, `invest` 1, `telegram` 11 — 131 call sites across `worker/routes`) and `audit()`, i.e. writes `rate_limits` and `audit_log`, which are not the moving service's tables. The platform kit therefore ships, in slice 1.2, drop-in replacements with the same signatures — `rateLimit(c, bucket, limit, window)` over `IDENTITY.rateLimitHit` (§3.6) and the `audit()` facade (ADR-012) — and every move slice's checklist includes "replace `worker/lib/{ratelimit,audit,session}` imports with the platform kit" before the first dark deploy, pinned by this test.
3. **The core's tolerance list.** `worker/OWNERSHIP.tolerance.json` (new) enumerates every foreign-table write the legacy core still performs, with the reason and the phase that removes it (e.g. `wallet_transactions by routes/orders.ts — B1, removed 7.1`). A snapshot in `tests/fixtures/` is only ever shrunk by a reviewed commit; the test fails on any new entry.
4. **Cross-domain batches** (assessment §2.2) are classified: (a) *intra-deployable after the merge* — B1's cart/coupon/settlement statements, B2/B3's points+wallet, B8, B9 (until Subscriptions splits), B10, B11, B13 stay batches; (b) *saga* — B1's ledger/points/inventory legs, B4, B5, B6, B14, B16; (c) *event* — B7 (credit by key then local rows), B12, B15. Every saga is written as: idempotent remote commands first (safe to retry), local batch second (carries the outbox row), remote commit third; the orchestrator's `<svc>_sagas` row records step state; a sweep (cron today, Workflow later) completes or compensates any saga older than 2 minutes still in progress.
5. **No SQLite schema prefixes** (renaming tables touches data). Ownership is by manifest. On PostgreSQL each service gets its own schema (`ledger.*`, `orders.*`, `identity.*`) and its own role with grants limited to that schema.
6. **Migrations.** `migrations/` stays the single D1 stream, applied by workflow 7 before code (`deploy-staging-code.yml:133` then `:337`; DECISIONS row 36) until a service has its own database. Every file `0055+` names its owning service in its header, touches only that service's tables, and must pass `scripts/check-migrations-additive.mjs` extended to accept `ALTER TABLE … ADD COLUMN` (SQLite-safe) — today the classifier treats every `ALTER` as destructive and is applied only to `studio/drizzle`, while 38 of the main-stream files contain `ALTER TABLE`; the extension and its scope (`0055+`) are pinned in `tests/migrationsAdditive.test.ts`. Own-store services keep `services/<name>/migrations/` applied by their own workflow before their code.

## 3. Edge: the gateway Worker

### 3.1 What it is

The only new Worker with zone routes. **What is attached today is not three routes**: per `docs/WORKERS.md` and `docs/SUBDOMAIN_ARCHITECTURE.md` §7.2/§7.5.1, `levonis-iq.com` and `www.levonis-iq.com` are Worker **Custom Domains** of `levonis-staging` (a Custom Domain cannot be re-pointed; it is detached — Cloudflare deletes the DNS record it manages — and re-attached with a new record and certificate issuance, a visible apex outage, not a "minutes" rollback), and only `*.levonis-iq.com/*` is a zone route. Workflow 12's read-only "Worker custom domains on this account" step records the attachment type per hostname before G3 (plan 3.0).

The cut-over is therefore a **route add, not a route move**: the gateway receives `levonis-iq.com/api/*`, `levonis-iq.com/files/*`, `www.levonis-iq.com/api/*`, `www.levonis-iq.com/files/*`, `*.levonis-iq.com/api/*`, `*.levonis-iq.com/files/*`; the Custom Domains and the wildcard `/*` route stay on `levonis-staging`, whose asset layer keeps serving `index.html`, chunks, CSS and images **without any Worker invocation**, exactly as `run_worker_first: ["/api/*","/files/*"]` does today. Rollback of the cut-over is deleting those six routes (seconds; DNS untouched). Two facts are proven on the dark zone in slice 1.0 before the plan depends on them: (i) a zone route for `<host>/api/*` wins over a Custom Domain's Worker on the same hostname; (ii) the more specific `*.<root>/api/*` wins over the existing `*.<root>/*`. If (i) is disproven, the fallback (plan 3.0-alt) converts the apex/www Custom Domains into a proxied DNS record + `levonis-iq.com/*`, `www.levonis-iq.com/*` zone routes **still targeting `levonis-staging`** (no behaviour change, verified by the live probes) as a separately approved pre-step, after which the cut-over is again a route add. `studio.levonis-iq.com/*` keeps pointing at `levonis-studio-staging` (exact host beats wildcard; re-verified after every route change). Consequences: the SPA never runs through two Workers; `loadSessionUser` is never executed per asset; workflow 7's byte-identity proof (`levonis-iq.com/assets/<hash>.js`) keeps meaning what it means today; the gateway needs no `assets` block until Phase 9, when the owner chooses between keeping the SPA on the core's Custom Domain and moving it to a gateway `assets` block (same `dist`, same `run_worker_first`, same `not_found_handling`, `_headers` from `scripts/write-asset-headers.mjs`).

It holds no business logic and no domain tables. Its code is `worker/index.ts:57-104`, `lib/hosts.ts`, `lib/securityPolicy.ts`, `lib/http.ts:57-104` moved into `packages/platform-kit/src/edge/*`, plus routing, principal resolution, limiting, caching, Turnstile and correlation. The Admin BFF is **not** in the gateway (row 21, ADR-015). Until G3 a var `GATEWAY_LOCKED=on` makes the production gateway answer `403` to every request that does not carry `x-health-probe: <HEALTH_PROBE_TOKEN>`; it is smoke-tested on a dark-zone hostname routed to it (plan 3.1), never on workers.dev (`workers_dev:false`, `preview_urls:false` from its first deploy).

### 3.2 Request pipeline (in order)

1. `x-correlation-id`: mint UUIDv7, or accept from a trusted internal caller only; browsers' values are ignored; echoed on every response.
2. Strip inbound `x-levonis-*` headers (Studio's strip-then-set pattern, `studio/worker/auth/session.ts:229-245`).
3. `classifyHost` (unchanged code) → `HostInfo`; `foreign && underRoot` → 404 as today.
4. `originCheck` for non-GET (unchanged) plus `Sec-Fetch-Site` sanity where present.
5. Request validation: method allowlist per route; **when a body is present** (`Content-Length > 0` or `Transfer-Encoding` set) a mutation must be `application/json` or `multipart/form-data` — bodiless `POST`/`DELETE` (the SPA's `api.delete()` and bodiless `api.post()`: `/api/auth/logout`, `/api/auth/verify-email/send`, cart-line removal, address deletion, `/api/marketplace/offers/:id/accept`, order cancel — 41 call sites in `src/`) send no `Content-Type` and must pass; body ≤ 1 MB except the **upload size classes**, generated from the code rather than guessed: `tests/gatewayUploadClasses.test.ts` (new) scans `worker/routes` for `formData()`/`arrayBuffer()` (today: `uploads` 8/40 MB image/video, `kyc` 8 MB, `marketplace` model files `MODEL_MAX_BYTES` 40 MB, `printRequests`, `adminImport` ZIP 40 MB / CSV 4 MB, `template` ZIP 15 MB, `devices` claim media 8/40 MB, `reviews` media 8/40 MB) and fails when such a mount lacks a gateway size class; reject `..` path segments and `Transfer-Encoding` tricks. The parity corpus contains one `DELETE`, one bodiless `POST` and one upload per such route.
6. Route lookup (§3.3). Unknown `/api/*` or `/files/*` → `CORE` (strangler default) until Phase 9, then 404 JSON.
7. Session → principal (§3.4); never blocks anonymous routes. Skipped entirely when the target is `CORE` and `PRINCIPAL_MODE` for the route class is `off` (the core runs `loadSessionUser` itself — no second session read per request; the host part of the capability guard still applies); in `shadow` the lookup runs for a sampled share (`PRINCIPAL_SHADOW_RATE`, 5 % → 100 % for the final week before `on`).
8. Capability guard for admin surfaces (§3.5): host rule always; role and scope from the principal once the class is `on`.
9. Rate limit (§3.6) — after the principal, so `user`/`money`/`admin-write` classes key by `sub`/`sid_hash`, not by IP: 429 body `{success:false,error:'Too many requests, try again later',code:'RATE_LIMITED'}` (matches `http.ts` `tooMany`).
10. Turnstile on flagged routes (§3.8).
11. Cache lookup for cacheable anonymous GETs (§3.7).
12. Forward over the binding with the principal header, a hop envelope (§4.3 — signed over method, args hash and principal hash; the callee **verifies** it: `GATEWAY_ONLY=off|log|on` on the core and every service, `403 NOT_VIA_GATEWAY` once `on`), the correlation id, `x-levonis-host: <kind>;<slug>` (covered by the envelope), `Host` untouched; the `Cookie` header goes only to `CORE` (strangler) and `IDENTITY`; every other service never sees it.
13. Response: `securityHeaders()` (idempotent; the core still sets them until Phase 9), `x-correlation-id`, `Server-Timing: gw;dur=…,svc;dur=…`, `Cache-Control: private, no-store` on anything with a principal, `Set-Cookie` **stripped** unless the upstream is `IDENTITY` or `CORE` (only Identity may set the session cookie), `x-levonis-challenge` and every other `x-levonis-*` internal header stripped, `x-levonis-legacy-path: 1` on legacy aliases so the 410 decision has usage data.

### 3.4 Session validation without owning `users` (ADR-002)

- Cookie `levonis_session`: HttpOnly, Secure, Lax, `Domain=.<root>` computed by `sessionCookieDomain()` — unchanged. Identity remains the only Worker that sets or clears it; `Set-Cookie` passes through the gateway unmodified.
- Gateway computes `sha256(token)` (as `session.ts:60`) and calls `IDENTITY.resolveSession(hash, {host_kind, cid})`. Identity runs today's query (`session.ts:63-69`), enforces expiry, and returns a **signed principal**: `{v:1, sub, sid_hash, role, scope, investor, tier, locale, host_kind, iat, exp: iat+120, cid}` signed Ed25519 (`IDENTITY_SIGNING_KEY`, `kid` in header). `scope` is `'owner'|'full'|'assistant'|null` — Identity folds the owner rule (`adminScope.ts:40-46`, `INITIAL_ADMIN_EMAIL`) into the signed claim, so no service needs the email to keep the owner-cannot-be-demoted guard or `canViewFinancials`. No `password_hash`, `google_sub`, email or phone.
- Gateway caches the principal in-isolate ≤30 s keyed by **`(sid_hash, host_kind)`** (LRU 10k) — a user who opens the apex and a merchant storefront within 30 s must not receive the first principal on both — and **only for read classes**; `money` and `admin-write` classes resolve per request (no cache), so logout and role changes are immediate where they matter; `IDENTITY.revoke(sid_hash)` from logout/password change evicts, and `SessionRevoked`/`RoleChanged` events reach the gateway's `deliver()` from Phase 3 (the 30-s TTL bounds the rest; shorter than Studio's 60-s cache today). KV negative cache later.
- Header `x-levonis-principal: <base64url(payload)>.<sig>`. Services verify with Identity's public keys (`IDENTITY.getPublicKeys()` cached 5 min; registry `service_keys`), reject expired principals, and compare `principal.host_kind` with the gateway-set `x-levonis-host` (kind + slug, covered by the hop envelope) — a mismatch is a 403 and an `AuditRecorded`. The platform kit's `principalToSessionUser()` reconstructs the `c.get('user')` shape route code expects; fields it **cannot** fill — `email`, `phone`, `profile_json`, `bio`, `checkin_streak`, `google_sub` — are documented in its type, and each extraction slice greps the moved routes for them (notifications, invoices, deposit receipts read `user.email`/`user.phone` today) and replaces the read with `IDENTITY.contactFor` (Notifications only) or removes it.
- Why Identity signs, not the gateway: a compromised gateway can then replay but not mint a principal.
- Strangler mode (Phases 3–8): the core still runs `loadSessionUser` from the cookie; the gateway forwards the cookie to `CORE`. `IDENTITY` = the core's `IdentityEntrypoint` (same code, same D1) until Phase 9. **Shadow runs in Phase 3.3, not Phase 9**: the core receives both the forwarded cookie and the forwarded principal, compares `loadSessionUser()` with `principalToSessionUser()` on the sampled share (`PRINCIPAL_SHADOW_RATE` 5 % → 100 %) and logs mismatches; **`PRINCIPAL_MODE=on` for a route class is the entry criterion of the Phase-4 slice that moves it** — a leaf service (KYC decrypting PII, Chat, Files, Support, Invest, Farm) never sees the cookie and owns no `sessions`/`users`, so from its first production request it accepts only a valid Identity-signed principal or a gateway-signed `anonymous`/`system` marker and rejects everything else (`401`). 9.1 re-runs shadow only for the binding re-point to `levonis-identity`.

### 3.6 Rate limiting

Adapter `RateLimiter` with the same key derivation as today (`rateLimitKey` from `lib/ratelimit.ts`, pinned by `tests/rateLimitKey.test.ts`). The only cross-isolate counter that exists today is the D1 fixed window in `lib/ratelimit.ts:48-56`; the target must never be weaker than it on any route, and a per-isolate bucket is trivially bypassed by spreading requests over colos. Layers, all shipped in slice 1.2:
- `D1RpcRateLimiter` — **the authoritative layer from day one**: `IDENTITY.rateLimitHit(class, key, limit, window)` — an RPC on the core's `IdentityEntrypoint` (Identity owns `rate_limits`, §2.1) running today's upsert verbatim; the default adapter for the gateway and for every extracted service (their moved `rateLimit()` calls keep their signature and go through it), so no extraction ever loses a cross-isolate limit. Cost: one D1 write per limited request, as today; used for `auth`, `money`, `upload`, `admin-write`, `write` and `webhook` classes.
- `BindingRateLimiter` — wrangler `ratelimits: [{ name, namespace_id, simple: { limit, period } }]`, one binding per class; `env.RL_<CLASS>.limit({ key })`. **Needs no created resource and no token scope** (`namespace_id` is a developer-chosen integer; plan §13.2 (b)), so the dark gateway uses it from slice 1.5 and production from 3.3 — but it counts **per colo**, so it is the cheap first layer for `ip` and `public-read` (which have no counter today) and a pre-filter in front of the D1 layer, never the only limiter on an `auth`/`money` route.
- `DoRateLimiter` — a `RateLimitCounter` Durable Object (SQLite, deploy-only class) sharded by key hash: the cross-isolate layer that replaces the D1 upsert when DO is approved.
- `MemoryRateLimiter` — per-isolate token bucket, dark/local only.

**Rule: no gateway class may be tighter than the bucket the core enforces today for the same route** — `tests/rateLimitParity.test.ts` (new) extracts every `rateLimit(c, bucket, limit, window)` call site from `worker/routes` and fails if a gateway class over that route has a lower limit. Consequences on the earlier draft: Telegram status poll stays **240/min per IP** (`auth.ts:1269-1271` — Iraqi carrier NAT puts many customers behind one IP and the SPA polls every 3 s, `TelegramAuth.tsx`), not 60; the new `ip` and `public-read` classes (no counter exists today) ship in **shadow/log-only mode with `/24` telemetry for two weeks** before enforcement, and their limits are set from the observed p99 of one NAT IP's boot fan-out (`/api/storefront/resolve`, `/api/auth/me`, `/api/settings/public`, `/api/wallet`, `BrowseMissionTimer`, `NotificationBell`, cart and farm polls), not from the placeholder numbers below; bearer-authenticated server-to-server routes (`/api/studio/handoff/redeem|introspect` — Studio's calls arrive from shared Cloudflare egress IPs — and `/api/telegram/webhook`) are exempt from the `ip` class and keep their own classes.

Classes (placeholders for `ip`/`public-read` until the shadow fortnight): `ip` (+ a looser `/24` bucket); `user` 300/min; `auth` (ip + `identifierKey()`) login 10/10 min, register 5/h, forgot 5/h, Telegram status poll 240/min; `money` (user) deposit 10/h, withdrawal 5/h, checkout 20/h; `write` 120/min per user; `upload` 30/10 min; `admin-write` 600/min (previously unlimited); `public-read` per ip on catalogue/home/storefront/farm leaderboard (previously unlimited); `webhook` 300/min. The gateway emits `RateLimitHit` (sampled, best-effort delivery) to Analytics/Risk.

## 4. Zero trust between services

1. **Reachability.** Internal Workers have no route, `workers_dev:false` **and `preview_urls:false`** (every environment block); the only way in is a service binding, and only Workers on this account can declare one. Coarse layer only — so every internal Worker **and the core** verify the gateway hop envelope on inbound HTTP: `GATEWAY_ONLY=off` (today) → `log` (one release after G3, counting requests that did not come through the gateway) → `on` (`403 NOT_VIA_GATEWAY`); in Phases 3–8 the core accepts cookie auth only when the envelope is valid, so `levonis-staging.<sub>.workers.dev` — where `adminAllowedOn()` returns true because the host is foreign — stops being a second door the moment `workers_dev:false` lands at G3, and `verify-live-security-headers.yml` asserts the workers.dev hostname no longer answers.
2. **Principal.** Every user-originated call carries the Identity-signed principal (§3.4). A service verifies signature, `exp`, `host_kind` against the route's host rule, and re-applies its own authorization (`requireAuth/requireAdmin/requireFinancial` from the platform kit over the principal). Server-side authorization per endpoint stays in the service.
3. **Hop envelope (service → service).** Each Worker has its own Ed25519 keypair (`<SVC>_SIGNING_KEY` secret; public key registered in `service_keys` owned by Identity, plus a bootstrap allowlist var `ALLOWED_CALLER_KIDS` before Identity exists). Every RPC carries `ctx = { cid, principal?, idempotencyKey?, hop: { iss, kid, iat, exp: iat+30s, nonce, method, args_hash: sha256(canonical(args)), principal_hash?: sha256(principal header) } }` signed by the caller from day one (adding `args_hash` later would change every client/server signature); retries re-sign with a fresh nonce. The callee verifies `iss` ∈ allowed callers **for that method** (e.g. `LEDGER.credit` accepts `commerce, marketplace, reviews, subscriptions, referrals, ledger-admin`; `LEDGER.decideDeposit` accepts only `notifications, ledger-admin`), verifies the signature, `args_hash` and `principal_hash`, and rejects replays by `(iss, nonce)` in a 60-s in-isolate set (behind the `Serializer`/KV adapter when available). Money methods additionally apply an **argument policy per caller** (item 7). No shared long-lived secret between services; rotation = add a `kid`, deploy callees, rotate the caller, retire the old `kid` after 10 minutes. The single shared secret today (`STUDIO_HANDOFF_SECRET`) is retired when Studio calls `IDENTITY` over a binding.
4. **System principal.** Cron/queue work uses `principal = { sub:'system:<svc>', role:'system' }` signed with the service key; callees authorise system principals per method (`INVENTORY.restore` accepts `system:commerce`, not `system:analytics`).
5. **Least privilege per Worker.** Each `wrangler.jsonc` declares only the bindings in §1.2; secrets exist only on the Worker that uses them (`EMAIL_*`/`TELEGRAM_*` → Notifications; `KYC_ENC_KEY` → KYC; `ALWASEET_*` → Fulfilment; nothing money-related on the gateway). `tests/leastPrivilege.test.ts` (new) diffs each service's declared bindings against `services/<name>/OWNERSHIP.json` (`calls`, `secrets`) and fails on anything undeclared; it also pins the **gateway's** `calls` to exactly `IDENTITY.resolveSession`, `IDENTITY.revoke`, `IDENTITY.getPublicKeys`, `IDENTITY.rateLimitHit`, `*.deliver` (for `SessionRevoked`/`RoleChanged`), `*.health` and the HTTP forward — no method containing `Admin`, `set`, `credit`, `debit`, `decide` or `lookupContacts` may ever appear there (ADR-015); and it fails on any non-gateway wrangler file lacking `workers_dev:false` + `preview_urls:false` in every environment. Studio's `IDENTITY` stub is allowlisted for `redeemHandoff` and `introspect` only (never `resolveSession`, a principal-minting oracle). The deploy workflow uploads only that service's secret names.
6. **Admin vs user APIs.** Separate router files per service (`src/http/admin.ts`, `src/http/public.ts`) mounted under `/api/admin/<domain>` or `/api/<domain>/admin`, gated at the gateway (host + role + scope) and in the service. Admin RPC methods carry `Admin` in the name and require `role:'admin'` plus non-assistant scope where money/PII is involved.
7. **Money methods.** Any RPC tagged money (`credit, debit, hold, commitHoldAndDebit, releaseHold, refund, decideDeposit, payout, grantCoins`) refuses to run without an `eventKey`, and its batch carries an `AuditRecorded` outbox row — a sensitive mutation cannot succeed unaudited (replaces the swallowing `audit()` at `lib/audit.ts:14-16`). Per-method allowlists are not enough for money — a compromised Reviews Worker (it parses user-uploaded media) could otherwise `credit({currency:'USD', amount: 1e8})` — so the Ledger applies an **argument policy per caller** in `packages/contracts/src/rpc/ledgerPolicy.ts` (new): `{ currencies, refTypes, maxAmount, dailyCap }` — Reviews: `POINT` only, `ref.type='review'`, amount ≤ the configured award; Referrals: `ref.type='referral'`, configured reward; Subscriptions: `ref.type='membership'`, refund ≤ paid; Marketplace: `ref.type ∈ {escrow, store_order}`; Commerce: `ref.type ∈ {order, return, price_protection}` with amounts ≤ the settlement (`PAYMENTS.settlementOf`). Violations return `FORBIDDEN`, emit `AuditRecorded` + `RiskFlagRaised`, and are pinned by `tests/ledgerPolicy.test.ts` (new). Deposit approvals are verified by Ledger itself (§6.5), never trusted from Notifications.
8. **Output filtering.** Cost, commission, internal notes and payout destinations are stripped in the owning service's projections (`projectPublic`, `withdrawalPublic`, `adminScope.ts` strip) — carried over verbatim; the assessment's leaks (`storeOrders.ts:227` `SELECT *`, `admin.ts:357` v1 products, `admin.ts:1690` settings blob) are closed with explicit column lists in Phase 0/4/6.
9. **Input validation.** HTTP handlers keep `str/int/pickFrom/oneOf` (`http.ts`) or a schema; RPC methods validate command objects with the `packages/contracts` validators (hand-written, no new dependency) so a compromised caller cannot pass malformed commands.
10. **Idempotency contract.** Every mutating RPC and every `POST/PUT/PATCH/DELETE` under `/api/v1/*` accepts an idempotency key (`Idempotency-Key` header / `ctx.idempotencyKey`). The key is client-supplied, so the store is **scoped to the caller**: `<svc>_idempotency (service, scope, key) → status + payload_hash [+ body]` where `scope` = `principal.sub` (or `anon:<ip-hash>` for anonymous routes) for HTTP and the hop `iss` for RPC — user B replaying user A's key never receives A's response. Keys shorter than 16 characters are rejected (`400`); the SPA mints keys with `crypto.randomUUID()` (replacing the `Date.now()+Math.random()` minting in `src/lib/api.ts:705`). Bodies are stored (24 h TTL) only for mutating routes whose response cannot be recomputed; auth, KYC and wallet routes store status + `payload_hash` only and re-execute the idempotent command on replay. Same key + different `payload_hash` → `409 IDEMPOTENCY_MISMATCH`. The core's `POST /api/admin/wallet/credit` (landed in `69ee814`) already behaves this way and is the reference implementation.

## 5. Event bus (details in `03-EVENTS.md`)

- **Envelope**: `event_id` (UUIDv7), `event_type`, `version`, `created_at`, `source_service`, `correlation_id`, `causation_id`, `actor_id`, `aggregate_type`, `aggregate_id`, `aggregate_seq`, `pii_class`, `delivery` (`'transactional' | 'best_effort'`), `payload`, `sig` (Ed25519 by the producer's `<SVC>_SIGNING_KEY` over the canonical envelope minus `sig`). Schemas in `packages/contracts/src/events/v1/<EventType>.ts` (new) with per-field `pii` annotations so Analytics/Ads projections strip mechanically. **Events are authenticated**: `subscriptions.ts` carries a per-event-type `producers` allowlist; `defineConsumer` verifies `sig` against the producer's registered key and refuses an envelope whose `source_service` is not an allowed producer of that type (and, in RPC mode, whose hop `iss` differs) — `SubscriptionChanged{to_tier:'gold'}`, `RoleChanged`, `KycDecided`, `ReviewPosted` grant privileges, so a Worker that merely holds a producer binding must not be able to forge them in queue mode.
- **Producer**: transactional outbox in the producer's own store (`<svc>_outbox_events`, `<svc>_outbox_deliveries`, `pump_lock`) **for `transactional` events only**; the outbox INSERT rides in the same `db.batch()` as the business write (the pattern `notifyStatement` already uses, `lib/notifications.ts:66-72`); the platform kit's `Uow` refuses to commit a command declared as publishing without its outbox statement. `best_effort` telemetry (`ProductViewed`, `AddToCart`, `CartCleared`, `FarmEvent`, `RateLimitHit`, `SearchQueried`, `TurnstileFailed`) never touches the producer's D1: it is sent fire-and-forget over RPC in `waitUntil` (Analytics Engine sink later) — 5–8 D1 writes per page view in the customer database, retained 180 days, bought nothing. After the batch, `ctx.waitUntil(bus.pumpIds(justCommittedEventIds))` delivers **only the events this request wrote** (no global lock, no `SELECT pending` on the shared single-writer database per request); the service's per-minute cron is the only `pump_lock` holder and the sweeper for everything the post-request pump missed. On the live core this sweep runs at the core's cadence until G2 adds the `* * * * *` trigger (plan 2.2), so the SLO for `source_service:'core'` events is 15 minutes until then.
- **Dispatcher**: `RpcFanoutBus` today (pump selects pending rows in `seq` order, fans out to subscribers from the static map `packages/contracts/src/subscriptions.ts`, calls `env.<CONSUMER>.deliver(batch)` — ≤50 events **and ≤500 KB serialised** per call (RPC arguments have a size ceiling; `OrderCreated`/`AuditRecorded` envelopes are large) — with backoff `min(15 min, 5 s·2^attempts)` + jitter, 8 attempts, then `state='dead'` — the DLQ is the deliveries table, replayable by an admin RPC). Delivery state is written with **one statement per `deliver()` call** (`UPDATE … WHERE event_id IN (≤50 ids)`, under D1's 100-parameter cap), never per event; a pump run is budgeted at ≤600 D1 statements and ≤60 RPC calls (D1 caps 1,000 queries per invocation on Paid; `waitUntil` is cut at ~30 s) and leaves the rest to the next cron. `QueueBus` when Queues exist — **one queue per consumer service** (`levonis-events-<consumer>` + `levonis-events-<consumer>-dlq`), because a Cloudflare Queue has exactly one consumer Worker; each producer declares `queues.producers` for every subscriber in `subscriptions.ts`, `pump` calls `env.Q_<CONSUMER>.sendBatch()` per subscriber in chunks of ≤100 messages / ≤256 KB with a per-envelope check (>100 KB → the envelope stays in the outbox and a pointer is sent; single messages are capped at 128 KB), consumers declare `max_batch_size: 50, max_retries: 8, dead_letter_queue`, and the same `deliver()` is called from `queue()`. Switch = `EVENT_BUS_MODE` var + binding presence; the topology is fixed now so the switch is config, not a rewrite. Cost note: in queue mode each event costs (write + read + delete) × subscribers — `OrderCreated` with 13 subscribers is ~40 billable operations per order; payload allowlists stay small.
- **Consumer**: `<svc>_processed_events (event_id PK)` inserted in the same batch as the side effect; remote-command effects derive their `eventKey` deterministically from the event or the domain key (`wtx_review_<id>`); money consumers keep domain idempotency (`ledger_idempotency`, `inventory_ledger.idempotency_key`, `orders.idempotency_key`) so correctness never depends on the event layer.
- **Poison**: schema-invalid or unsigned/wrong-producer events are recorded `result='invalid'`/`'forged'` (the latter also emits `RiskFlagRaised`) and never retried; ordering is per aggregate (`aggregate_seq`), consumers tolerate reordering ("last `aggregate_seq` wins"); replay from any producer's outbox is safe by construction.
- **Interim on the live core**: the core is a producer too (`core_outbox_events`, migration `0056`), **behind `EVENT_BUS_ENABLED=off` by default**: `publishStatement()` returns no statement while the var is off or while the outbox table is absent (a boot probe caches `PRAGMA table_info(core_outbox_events)` per isolate), so code that merges before workflow 7 has applied `0056` cannot fail a checkout or a signup with "no such table" (the incident of `DECISIONS.md` row 36). Once `0056` is applied and the var is `on`, rows accumulate before consumers are bound (Phase 2) and are pumped once bindings exist — no event between the migration and the binding is lost.

## 6. Money (ADR-006)

### 6.1 Boundary and contract

The Ledger package is the only writer of `wallet_transactions`, `wallet_holds`, `wallet_adjustments`, `points_*`, `ledger_balances`, `ledger_idempotency`. `merchant_payout_ledger` (IQD merchant accounts) is written only by Marketplace through its own `payout` commands with the same rules (keys, conditional flips). The contract, exposed from the core's `LedgerEntrypoint` from Phase 2 and from `levonis-ledger` from Phase 8:

```ts
type MoneyCmd = { eventKey: string; userId: string; currency: 'USD'|'POINT'; amount: number;
                  ref: { type: string; id: string }; reason: string; actor: Actor; correlationId: string };
interface LedgerApi {
  credit(cmd: MoneyCmd): Promise<Applied>;                 // approved deposit row
  debit(cmd: MoneyCmd): Promise<Applied|Refused>;          // conditional withdrawal row (usdSpendStatement semantics)
  hold(cmd: MoneyCmd & { kind: 'purchase'|'withdrawal'|'escrow' }): Promise<HoldResult>;   // wallet_holds conditional insert (walletOps.ts:228-258)
  commitHoldAndDebit(cmd: { holdId; eventKey; txId; note }): Promise<Applied|Refused>;      // NEW atomic: withdrawal row + hold→committed in one batch
  releaseHold(cmd: { holdId; eventKey }): Promise<Applied>;
  refund(cmd: MoneyCmd): Promise<Applied>;                 // credit with ref.type ∈ {order, return, price_protection, escrow, membership}; ids wtx_refund_<id>_usd|_pts kept
  reservePoints(cmd), settlePoints(cmd), releasePoints(cmd), reversePoints(cmd);           // existing pointsOps statements behind the API
  decideDeposit(cmd: DepositDecisionRequest): Promise<DepositDecisionResult>;             // the ONLY approval path
  getBalances(userId), getBreakdown(userId), reconcile();
}
type Applied = { ok: true; applied: true; txIds: string[] } | { ok: true; applied: false; replayed: true; txIds: string[] };
type Refused = { ok: false; reason: 'INSUFFICIENT'|'EVENT_KEY_REUSED'|'INVALID_AMOUNT'|'STATE_CONFLICT'|'FORBIDDEN' };
```

Every command **requires** `eventKey`. The deterministic ids already in use (`wtx_ord_<id>_usd`, `wtx_refund_<id>_usd`, `wtx_ret_<caseId>`, `wtx_pp_<claimId>`, `wtx_review_<id>`, `wtx_acc_<accrual>`, `wtx_refund_<membershipId>`) become the keys, so behaviour is unchanged and replay-safe across Workers. **Keys are server-minted**: the contract form is `<service>:<aggregate>:<server id>:<leg>` (or the legacy deterministic ids above); a client idempotency key maps to a server key only through the caller's own table (`orders.idempotency_key` → `orderId`, so store checkout uses `store:<orderId>`, never `store:<client key>`), and `tests/serviceBoundaries.test.ts` fails on any `eventKey` built from a request header or body field. A replay is only a replay when `user_id` and `payload_hash` match the stored command; the same key with a different user, amount or currency is `EVENT_KEY_REUSED` (409) plus an audit/risk event — otherwise user B could shadow or block user A's command by guessing a key (`wallet_transactions.event_key` is globally unique while `wallet_holds` is unique per user, `0015_wallet_holds.sql:58`).

### 6.2 Journal, append-only, balances

- `wallet_transactions` remains the journal (constraint 5). Additive migration `0055_ledger_keys.sql` (new): `ALTER TABLE wallet_transactions ADD COLUMN event_key TEXT; ADD COLUMN correlation_id TEXT; ADD COLUMN source_service TEXT;` + `CREATE UNIQUE INDEX … ON wallet_transactions(event_key) WHERE event_key IS NOT NULL` + the composite index `(user_id, currency, status, type)` the assessment asks for. Historical rows keep `NULL`; the application copies the deterministic id into `event_key` on first touch — no data migration.
- Append-only rule: new money movements are always INSERTs. The two legitimate UPDATEs (deposit `pending→approved|rejected`, the withdrawal state machine) are request state transitions, conditional on the old state, as today. `ledger_idempotency (event_key PK, user_id, command_type, payload_hash, result_json, created_at)` records every command outcome so a replay returns the same answer even when the command was refused, and so that a reuse with a different `user_id`/`payload_hash` is refused (`EVENT_KEY_REUSED`), never silently reported as `replayed`.
- Balances: `SUM` over approved rows (`walletOps.ts:44-61`) stays **the truth on D1**. `ledger_balances (user_id, currency, settled, held, revision, updated_at)` is a materialised cache written in the same batch as each journal insert with a revision fence (`UPDATE … SET revision = revision+1 WHERE user_id=? AND currency=? AND revision=?`; a mismatch aborts the batch and the command retries with a fresh read, ≤3 times). `reconcile()` (cron step 9 extended, `walletOps.ts:1167`) compares SUM vs cache and covers **purchase holds** (unchecked today), reports to Audit and never repairs silently.
- No path adjusts a balance alone: `lib/wallet.ts` `credit()` (no key) is replaced by `LEDGER.credit`; `admin.ts:514-526` manual credit gets `admin:full` + `eventKey` + rate limit + audit (Phase 0).

### 6.5 Payments today (no PSP)

Deposits are manual transfers with a receipt and Telegram admin approval; withdrawals are manual payouts with `WITHDRAWAL_TRANSITIONS`; COD settles on delivery via `order_payment_settlements`. The `PaymentProvider` adapter (`authorize/capture/refund/webhook`) exists from day one with `ManualTransferProvider` (today's behaviour) and `SandboxProvider`; a PSP is a new adapter plus secrets on the Ledger deployable only. `PaymentAuthorized` is emitted when a hold is placed, `PaymentCompleted` when a debit commits or a COD settlement is recorded, `PaymentFailed` when a hold fails.

**Telegram deposit approval across two Workers** (Notifications = transport, Ledger = decision; `lib/walletNotify.ts:1124-1180` today). Ledger mints an `approval_nonce` per deposit request, stores `sha256(nonce)` in `wallet_deposit_meta.approval_nonce_hash` (new column) and carries the nonce in `DepositRequested`; Notifications renders the admin message and buttons (`tg_admin_notifications`/`tg_admin_actions`, its tables) with the nonce. On `callback_query` Notifications forwards **only** `{update_id, telegram_user_id, nonce, chat_id, message_id}` to `LEDGER.decideDeposit`; Ledger verifies the nonce against its row (single use), verifies `telegram_user_id` against **its own** `admin_tg_identities`, applies the conditional flip (`amount_mismatch` refusal unchanged) and is the actor of record. The contract keeps today's semantics: Notifications answers the callback **after** the decision and after the authoritative re-read (`won`/`lost_race`/`decision_failed`), and only the message rewrite goes to `waitUntil`. A compromised Notifications can therefore neither approve without a real admin's Telegram identity nor replay a nonce. ### 6.6 The checkout saga (B1) — built inside the core first (ADR-007)

```
placeOrder(cmd, principal):                 # cmd carries orders.idempotency_key (existing per-user key, 0001_init.sql:156)
  0  existing order for (user, key) → return it (as today)
```

The fence on both sides closes the race the first draft had: without it the sweep could read `started` at T+120 s and release the hold while the request's step-6 batch committed at T+120.1 s, leaving a persisted, unpaid `pending` order whose `OrderCreated` had already started fulfilment, mailed an invoice and sent `PurchaseCompleted` to Ads. Now either the sweep wins (`compensating`, and step 6's guarded UPDATE changes 0 rows → the batch aborts, nothing persisted) or the request wins (`local_committed`, and the sweep's UPDATE changes 0 rows → no release). **Downstream effects that presume payment** (Fulfilment beyond `init`, Invoices' mail, Merchants' payout credit, Ads' `PurchaseCompleted`) subscribe to `PaymentCompleted`/`OrderPaid` for prepaid orders, never to `OrderCreated`; COD orders follow `OrderDelivered` as before.

Invariants pinned by `tests/checkoutSaga.test.ts` (new) with crash injection after each step **and** the two races: (a) an order row exists ⇔ an approved debit exists or the saga is `local_committed` and retryable; (b) no hold stays `active` for an order that does not exist; (c) stock reserved ⇔ order exists or reservation released; (d) replaying with the same idempotency key returns the same order and creates nothing; (e) sweep-vs-step-6: exactly one side wins, never both; (f) `POST /api/orders/:id/cancel` while `checkout_sagas` is not `done` is refused (`409 ORDER_SETTLING`) or serialised behind the saga row — today orders are independent and cancel could otherwise race step 7 (release-by-sweep vs refund vs `commitHoldAndDebit`, restore vs `INVENTORY.confirm`); (g) a `stuck` saga returns `ORDER_PENDING_SETTLEMENT` to the customer and is unblocked only by the admin RPC. `checkout_sagas UNIQUE(user_id) WHERE state IN ('started','local_committed','compensating')` blocks the customer's next order only while a saga is genuinely in flight (≤2 min + the sweep), and the stuck state is excluded from the index so a stuck saga never blocks the customer. Rows, ids and `wallet_transactions` semantics are identical to today's batch, which is what makes the `CHECKOUT_SAGA` flag safe to flip per request (10% → 100%). `initOrderStage` and invoice creation stay **synchronous** in step 8 (they are already replay-safe and the SPA reads `invoice_no` and the stage right after placing — `Checkout.tsx:545-566`, `OrderDetail.tsx:493`); the printer gift, Telegram/admin notifications and everything else in `orders.ts:1525-1575` become consumers. The invoice mail needs the customer's address: Invoices emits `InvoiceIssued`, and **Notifications** resolves the address through `IDENTITY.contactFor` (§2.4) — Invoices never holds a contacts permission. Store checkout (B4), escrow (B6/B14), membership purchase (B9) and cancel/refund (B2/B3) follow the same shape, including the fence, with their existing keys (`02-MIGRATION-PLAN.md`, §10).

| KYC review / retention | manual; retention never set | `KYC_REVIEW`: `waitForEvent('decision',{timeout:'30d'})` → `sleepUntil(retention_until)` → purge | KYC cron once retention is decided (DECISIONS row 24) |
| Subscription lifecycle | write-on-read expiry | `SUBSCRIPTION_LIFECYCLE` per membership | Subscriptions cron computes expiries and emits `SubscriptionChanged` |
| Import / template apply | synchronous, two batches per product | `IMPORT_APPLY`: parse → plan → apply per product (idempotent on `import_id,row`) → images via Queue | job id + poll endpoint (additive); `waitUntil` chunks |
| Checkout saga completion | none | `CHECKOUT_SAGA` for stuck sagas | Commerce cron sweep every minute |
| Escrow auto-complete / request expiry | missing consumer | `ESCROW_AUTOCOMPLETE` with `sleepUntil(auto_complete_at)` | Marketplace cron (new job) |
| Outbox message delivery | cron step 1 + `waitUntil` pumps | Queue consumer | Notifications cron + pumps |
| Withdrawal lifecycle | endpoints + reconciliation flags | `WITHDRAWAL_LIFECYCLE` | today's endpoints; cron for stale flags |

Adapter `ProcessRunner { start(name, input) }` with `CronSweepRunner` (records the intent in the owning table; the sweep does the work) and `WorkflowRunner` (`env.<WF>.create({id, params})`); the same step functions serve both. Every service gets its **own** cron trigger (Workers Paid; ~28 Workers on `* * * * *` is ≈40k cron invocations a day before any user traffic — counted in the plan's §13.2 cost column; the account cron-trigger cap is one of the slice-1.0 probes), which dissolves `lib/jobs.ts`'s 13-step single cron step by step; the core keeps a step until its owner has taken it, guarded by `LEGACY_DISABLED_STEPS` so nothing runs twice and the old behaviour is one var away. Workflow ceilings when adopted: `step.sleep`/`sleepUntil`/`waitForEvent` are bounded to one year per step, so a KYC retention longer than a year is chained in ≤365-day steps; one long-sleeping instance per membership/order/escrow can approach the account's concurrent-instance cap, so slice 1.0 probes whether sleeping instances count, and `CronSweepRunner` **stays the design** for per-row schedules with potentially thousands of concurrent waits (subscriptions, points release, escrow auto-complete) while Workflows are reserved for bounded multi-step processes (import apply, KYC review, checkout-saga recovery).

## 9. Ads and Analytics

### 9.1 Ads (`levonis-ads`)

```ts
interface AdsProvider {
  readonly name: 'meta_capi'|'google_ads'|'tiktok'|'snapchat'|'noop';
  configured(env): boolean;                                   // secrets present
  map(event: EventEnvelope, consent: ConsentState): ProviderEvent|null;
  send(events: ProviderEvent[], opts: { timeoutMs; correlationId }): Promise<{ accepted; rejected; error? }>;
}
```

- Providers `MetaConversionsApi` (server events; hashed `em`/`ph`; `event_id` = our `event_id` for Pixel dedup), `GoogleAdsOfflineConversions`, `TikTokEventsApi`, `SnapchatConversionsApi` — all stubs that validate mapping and write `ads_deliveries(status='sandbox')` when their secrets are absent; `NoopProvider` default. Mapping (`ads_event_map`, seeded): `PurchaseCompleted → Purchase`, `UserUpdated{marketing_consent→'ads', first time} → CompleteRegistration` (Ads never sees `UserCreated`: no consent can exist at signup), `AddToCart → AddToCart`, `CheckoutStarted → InitiateCheckout`, `ProductViewed → ViewContent`, `SubscriptionChanged{active} → Subscribe`.
- PII: Ads never receives `pii_class='personal'` envelopes (the bus refuses to deliver them to consumers with `piiMax:'pseudonymous'`). Hashing (SHA-256 of normalised email / E.164 phone) is done by **Identity, the owner of the contacts**, and only on a consent change: `UserUpdated{marketing_consent, email_hash, phone_hash}` (fields `pii`-annotated) → Ads keeps them in `ads_consent_snapshots` keyed by `user_hash`; `PurchaseCompleted` carries `order_id`, `user_hash`, value and items only, and Ads joins locally. Commerce therefore never holds a contacts permission (the earlier draft's "Orders via `IDENTITY.lookupContacts`" would have given the largest user-input surface a standing contacts dump); `lookupContacts` stays admin-only (§2.4). Ads drops every `pii` field at ingest when the consent snapshot is not `ads` — dropped before persistence, not merely recorded `no_consent`. Consent: `marketing_consent` (`none|analytics|ads`) profile column (new, default `none`); without `ads` consent the delivery is recorded `no_consent` and not sent.
- Kill switches: `CONFIG.flag('ads.enabled')`, `ads.providers.<name>.enabled`, `ads.events.<type>.enabled`; emergency = unset the secret → sandbox. Timeouts 5 s, 2 retries with jitter on 5xx/timeouts, circuit breaker per provider (open after 5 consecutive failures, half-open after 60 s). Nothing in Orders/Checkout imports or knows any provider.

### 9.2 Analytics (`levonis-analytics`)

Consumes an **explicit allowlist** of `none|pseudonymous` events (`03-EVENTS.md` §6 — the wildcard `'*'` is gone: it would have delivered `KycDecided`, `RiskFlagRaised`, `RoleChanged` and money movements keyed by raw `user_id` to the least-sensitive store); stores allowlisted payload projections in `analytics_events` (own D1 → `analytics_engine_datasets: EVENTS_AE` via the `AnalyticsSink` adapter); maintains `analytics_daily_platform(day, metric, value)` and `analytics_daily_merchant(day, merchant_id, metric, value)` idempotently by `processed_events`. Replaces over time: `admin.ts:125-159` overview aggregates, `merchant.ts:1443-1487` merchant analytics, the dead `merchant_store_analytics_daily`. Actor ids are hashed with a daily salt; every field annotated `pii` is dropped at ingest. Never on the hot path.

## 11. Observability and operations

### 11.1 Structured logs

```json
{"ts":"2026-09-07T10:00:00.123Z","level":"info","svc":"commerce","ver":"<git sha>","env":"production",
 "cid":"018f…","rid":"req_…","hop":"gateway>commerce","principal":{"sub":"usr_…","role":"customer"},
 "route":"POST /api/orders","status":200,"dur_ms":41,"db_ms":12,"db_stmts":3,
 "rpc_out":[{"to":"ledger","m":"commitHoldAndDebit","ms":9}],"msg":"checkout.saga.step","step":"ledger.hold","outcome":"applied"}
```
Never logged: tokens, cookies, secrets, full emails/phones, request bodies of auth/KYC/wallet routes. `console.log(JSON)` → Workers Logs (`observability.enabled` already on); `tail_consumers` to a log-sink Worker is a later option. Volume: one user request produces a gateway line, a service line, one per RPC hop, a `PumpReport` and consumer lines — 5–10 log events across ~28 Workers plus per-minute cron reports — and Workers Logs bills per million events beyond the included allowance, so every Worker sets `observability.logs.head_sampling_rate` (schema key) for `info` lines; `error` lines and money/audit outcomes are emitted unsampled (a second unsampled logger), and counters move to Analytics Engine (`writeDataPoint` is not a log event) as soon as the dataset binding is deployed.

### 11.2 Correlation
Gateway mints `cid`; every RPC passes `ctx.cid`; every envelope carries `correlation_id`; consumers set `causation_id` on events they emit; responses carry `x-correlation-id`; the SPA shows it on error toasts ("reference: …").

### 11.3 Health
Every service: RPC `health(): {ok, svc, ver, checks:{db, outbox_lag_s, deps[]}}` and HTTP `/health` on its dark URL. A production Worker with `workers_dev:false` has **no URL**, so its probe goes through the gateway (until G3: the core) at `GET /api/health?deep=1` with the `x-health-probe: <HEALTH_PROBE_TOKEN>` header (constant-time compare, rate-limited, or an `admin:full` principal on the apex), which fans out `health()` over every bound service with a 2-s budget and returns each service's `ver`; `probe-health.mjs --env production` calls that and asserts the deployed commit. A production Worker not yet bound anywhere (Phase 2.1 before G2) is proven by its dark twin's URL plus `wrangler tail` of one scheduled run. `/api/health` itself is forwarded to the core unchanged (§3.3).

### 11.4 Metrics
Log-line metrics today (`metric:` fields), `analytics_engine_datasets` later. Golden signals per service: request count/latency/error by route class, RPC latency by method, outbox lag, DLQ depth, saga in-progress count, ledger reconciliation anomalies, gateway cache hit ratio. SLOs: gateway p95 added latency < 150 ms; checkout saga p95 < 600 ms — a provisional number: service bindings run in the caller's colo but every leg round-trips to D1's single home region, so the number is fixed only after slice 1.0/7.1 measure the saga on dark with and without `placement: { mode: "smart" }` (schema key) on Commerce, Ledger and Catalog; bus delivery p95 < 5 s; DLQ = 0 (alert > 0); oldest pending event < 5 min for events produced by Workers with a per-minute cron and **< 15 min for `source_service:'core'` events until G2 adds the core's per-minute trigger** (the alert threshold follows the producer).

### 11.5 Timeouts, retries, circuit breakers
Every external `fetch` goes through `fetchWithBudget(url, init, {timeoutMs, retries, retryOn, ssrfGuard})` (`lib/fetchGuard.ts` moves into it): Resend 8 s/2, Telegram 5 s/2, Al-Waseet 15 s/0, Google JWKS 3 s/1, Turnstile 3 s/1, ads 5 s/2; a lint rule makes bare `fetch(` outside the platform kit an error. RPC: 3-s default budget (10 s for import/media), retries only for idempotent commands (all money commands are), never for forwarding a mutating HTTP request. Circuit breaker per (service, method) and per provider: open after 5 consecutive failures, half-open after 30 s; open → `503 DEPENDENCY_UNAVAILABLE`; money commands are never skipped on an open breaker — they fail the request.

### 11.6 Deploy pipeline, environments, secrets, rollback
- Monorepo (`npm workspaces`): `services/<name>/{wrangler.jsonc, package.json, src/, migrations/, OWNERSHIP.json, SECRETS.md, tests/}`, `packages/{platform-kit, contracts, pricing, shipping}`, `worker/` (core, in place), `src/` (SPA), `studio/` (unchanged). `npm run check` iterates workspaces (reusing the `scripts/check-studio.mjs` pattern) and runs the boundaries, least-privilege, ownership, schema, naming and bundle-budget tests.
- One reusable workflow `.github/workflows/_deploy-worker.yml` (new) + one `svc-<name>.yml` per Worker, display names `2x - Deploy DARK levonis-<svc>-dark (serves no domain)` / `3x - Deploy LIVE levonis-<svc>` with a confirmation phrase, all satisfying `tests/workflowNaming.test.ts` (extended). Steps: `npm ci` → `npm run check && npm run test:unit` → resolve resource ids by name (`wrangler d1 list --json`, as workflow 7) → carry the running Worker's vars forward (`scripts/prepare-deploy-config.mjs` logic extracted to `scripts/lib/preserve-vars.mjs`, new) → apply **that service's** migrations before code → **two-step first deploy**: the Workers upload API rejects a `services` binding whose target Worker does not exist yet, so `scripts/resolve-ids.mjs` strips every `services` entry whose target is absent from `wrangler deployments list`, deploys, and redeploys with the full binding set (idempotent; this is what makes self-bindings — `levonis-ledger` → `levonis-ledger` — and cycles — Ledger↔Notifications, Identity↔Notifications, Commerce↔Fulfilment — deployable) → `wrangler deploy -c services/<name>/wrangler.jsonc --env <env>` → upload only the secret names in `SECRETS.md` from repository secrets `<SVC>__<NAME>` → probe health (§11.3) → dark only: run the integration corpus → record the deployment id.
- Workflows 7 and 8 stay the live paths for the core and Studio. Workflow 7 gains, in Phase 0 (slice 0.0), two **generic, validated inputs** — `set_var NAME=VALUE` (names must exist in `wrangler.jsonc` `env.staging.vars`) and `upload_secret NAME` (names must be listed in `docs/SECURITY.md`/`worker/SECRETS.md`) — so that every core flag and secret this programme needs (`EVENT_BUS_ENABLED`, `EVENT_BUS_MODE`, `GATEWAY_ONLY`, `PRINCIPAL_MODE`, `PRINCIPAL_SHADOW_RATE`, `LEGACY_DISABLED_STEPS`, `CHECKOUT_SAGA`, `ALLOWED_CALLER_KIDS`, `LEDGER_TARGET`; secrets `IDENTITY_SIGNING_KEY`, `CORE_SIGNING_KEY`, `HEALTH_PROBE_TOKEN`) is a workflow run, not a hand-written special case or a dashboard edit — a "flag off" rollback is then a seconds-level var flip with a known propagation time (a var change is a deploy; ~30 s to all isolates). Until the Git integration is disconnected (G0), `scripts/prepare-deploy-config.mjs` folds `services` (and later `durable_objects`, `queues`, `kv_namespaces`, `ratelimits`, `workflows`) as it folds `d1`/`r2`/`vars`, so a Git-integration deploy cannot strip the core's bindings. `2 - Rebuild levonis-staging + run API tests` is re-pointed at the dark stack so test users never land in the live DB again (owner decision).
- Secrets: per Worker, uploaded by that Worker's workflow only; rotation = add `<NAME>_NEXT`, deploy code accepting both, switch, remove; `secrets_store_secrets` bindings when the account has a Secrets Store.
- Rollback: (a) code — `wrangler rollback` per Worker or redeploy the previous commit; (b) routing — kill switch or re-point a gateway binding/prefix to `CORE` (seconds); (c) cut-over — **delete the six `/api/*`, `/files/*` gateway routes** in the dashboard (seconds; the Custom Domains never moved, so there is no DNS or certificate to undo); (d) data — additive migrations only, never a down-migration; a service whose tables moved keeps dual-read for one phase; (e) binding re-points (Phase 8.1) — a var flip per caller between two declared bindings (`LEDGER_CORE`/`LEDGER_SVC`, selected by `LEDGER_TARGET`), not a redeploy per caller.
- The Workers Builds Git integration on `levonis-staging` is disconnected (owner action, **G0**, before any code that needs migration `0055+` merges to the default branch — SUBDOMAIN_ARCHITECTURE.md §7.5.3): the integration deploys every push ~60 s later with no migrations, so schema-dependent code would otherwise reach the live database ahead of its migration (DECISIONS row 36). Together with G0 comes the **two-PR rule**: a migration PR is deployed by workflow 7 before the PR that writes the new column/table merges.
- **Live verification follows ownership.** Each slice that moves a probed capability re-points the verification workflow in the same PR, per a table keyed by phase and pinned by `tests/workflowNaming.test.ts`: `verify-live-auth.yml` tails `levonis-staging` until 9.1, then `levonis-identity`; workflow 7's byte-identity proof fetches `levonis-iq.com/assets/<hash>.js` and compares to the core's build for as long as the SPA is served by the core (the whole programme unless 9.3 moves it, in which case the proof moves to `svc-gateway.yml`); workflow 7's read-only probe list uses a CORE-owned path per phase (§3.3); `verify-subdomains.yml` runs after every route change and every prefix flip.

## 12. What "nothing deleted or broken" means operationally

- Every path mounted in `worker/index.ts` keeps its method, path, envelope and status codes; `tests/routeTable.test.ts` (new) snapshots the mounted table of the core plus every service and fails on removal. 410s only by owner decision and they answer forever, as `index.ts:190-196` does.
- Every table and column stays; migrations `0055+` are additive.
- Every cron step keeps running somewhere (moved verbatim, flag-guarded so it never runs twice).
- Every row keeps its meaning: the saga writes the same ids and statuses as the batch; ledger rows keep their shapes; no phase requires a backfill.
- ar/en/ckb and merchant subdomains: `Host` forwarded untouched, the classifier is the same code, the cookie attributes the same function; `verify-subdomains.yml` runs at every flip. Because workers.dev has no `*.<root>` wildcard (`sessionCookieDomain()` returns null on a public suffix and `classifyHost()` answers `foreign` for every host), the merchant-host behaviour of the gateway is proven on the **dark zone** (plan §13.2: an owner-provisioned throwaway domain with a proxied `CNAME *` and routes to `levonis-gateway-dark`, `STORE_ROOT_DOMAIN`/`APP_ORIGIN` set on the dark core) with `scripts/e2e-subdomains.mjs` as the exit gate of 1.5 and 3.1 — the gateway's host-class table never meets its first real merchant host on the live wildcard.
- The SPA and its assets keep being served by the core's Custom Domains / asset layer with no Worker invocation until Phase 9 (§3.1); the parity corpus covers `/`, `/products`, `/assets/<hash>.js` (200 and 304) and `/files/products/*` so a later change to that path is measured, not assumed.
