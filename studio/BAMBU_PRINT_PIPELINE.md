LEVO supports explicit, user-controlled print handoffs today. The section below
describes the DESIGNED primary output action, «تجهيز لـ MakerWorld» (Prepare
for MakerWorld), which is not currently wired to any screen. Desktop users can additionally slice locally, download or share the actual `.gcode` (now a secondary/advanced action), then open/transfer it to Bambu Connect or Bambu Studio and verify the real printer state there. Phone-only users export the current Bambu/Orca-compatible `.3mf` project, upload it as a **Private Model** at MakerWorld themselves, and initiate the cloud print from Bambu Handy after verifying the printer and AMS. Supported removable storage remains the offline fallback.

## Designed primary output: «تجهيز لـ MakerWorld» (mandate §9) — NOT MOUNTED

Written in `app/export-manager.ts` (state machine, structural 3MF verification, output-kind classification) and `app/makerworld/prepare.tsx` (four-step UI over the S4 engine adapter). The flow has four honest steps:

1. **Preflight** (`app/makerworld/preflight.ts`) — build-volume bounds per object, plates (declared 9-plate engine cap), materials/extruders, profile-preset fallback, and the paint/format limitations from `docs/STUDIO_GAPS.md`. Blockers stop the flow; declared limits are shown, never hidden.
2. **Real 3MF preparation** — the engine's own save path (`save-project` through the S4 adapter). The produced file is verified structurally (ZIP central directory: `[Content_Types].xml` + a `3D/*.model` part) before it is ever labeled ready; an invalid or truncated file fails loudly and is not downloaded.
3. **Transfers summary** — what transfers (geometry, plates, transforms, global settings), what transfers **partially** with declared limits (per-object extruder assignment — written to `Metadata/model_settings.config` and fed to the slice request, but unverified in final G-code on this build; support paint — multi-plate projects persist imported paint only), and what does **not** transfer (surface/facet colors, embedded thumbnail, `slice_info.config`, a MakerWorld-accepted print profile).
4. **Official-path handoff** — the verified file is downloaded with a clear name (`LEVO-<project>-<printer>.3mf`) and the official MakerWorld upload page is opened. Labels are exactly "الملف جاهز" (file ready) and "فتح MakerWorld" (open MakerWorld). Opening the page is **not** an upload and is never presented as one; the state machine has no upload-success state at all (tested in `tests/makerworld-flow.test.mjs`).

### Mandatory output-kind distinction

| Kind | Status in LEVO today |
|---|---|
| Editable 3MF project | **Available and shipped** — `saveBambuProject` runs the engine save path and `bambu-project-3mf.ts` converts it into a Bambu project package. Uploads to MakerWorld as a model/project. |
| MakerWorld/Bambu Studio Print Profile | **Not possible.** MakerWorld's print-profile check rejects files not generated by Bambu Studio; LEVO does not fake one and does not present its 3MF as a print profile. |
| Sliced G-code | **Available — secondary/advanced.** Kept for tests, preview, USB and manual transfer; removed from the primary action. |
| `.gcode.3mf` printer package | **Gated** (`packagePrintJob: false`) until golden package fixtures pass — unchanged, see below. |

### No sanctioned third-party upload API

There is no official MakerWorld API/SDK or authorized third-party upload integration known to this project; the only endpoints observed elsewhere are reverse-engineered and unauthorized, and LEVO does not use them (mandate §9 forbids inventing endpoints or asking for Bambu/MakerWorld credentials). **Re-verification attempt, 2026-08-28:** the three reference URLs below plus `makerworld.com/en/faq` remained unreachable from the build environment (network egress blocked), matching the earlier survey. Re-checking them from an unblocked network — and any consented manual upload test with an owner-approved account — remains pending and is listed as such; the assisted prepare-and-open flow above is the implemented path either way, and direct upload would become possible only if an official integration appears.

### Test fixtures provenance (`tests/fixtures/`)

- `cube-10mm.stl`, `cube-300mm.stl`, `tetra-8mm.stl` — deterministic hand-written ASCII STL fixtures for preflight tests and for the in-browser slicing smoke (T10).
- `mini-project.3mf` — a hand-authored, structurally valid minimal 3MF whose entry names mirror the installed three-slicer 0.2.2 save writer (`[Content_Types].xml`, `_rels/.rels`, `3D/3dmodel.model`, `Metadata/model_settings.config`, `Metadata/project_settings.config`). It is **not** an engine export and has **not** yet been opened in Bambu Studio/Orca; that compatible-tool check (T11) still requires a real engine-saved export and stays with the verification pass. `broken-truncated.3mf` is its deliberately truncated sibling for negative tests.

Direct browser-to-printer/cloud networking is intentionally disabled. A browser cannot open the printer's raw LAN MQTT/FTPS transports, and Bambu Lab's cloud authorization control restricts critical cloud operations. A safe implementation cannot treat raw G-code as a drop-in printer job, claim a printer is connected without live evidence, call an undocumented private cloud API, ask for the user's Bambu account password, or assume that a browser knows the downloaded file's absolute desktop path.

## Required gated pipeline

1. **Generate** — accept a successful in-volume slice and freeze its settings, profile ID, model checksum, and G-code checksum.
2. **Package** — build a deterministic Bambu-compatible `.gcode.3mf` containing the required metadata, thumbnails, plate mapping, printer profile, and G-code entries.
3. **Validate** — reopen the package, verify its ZIP/3MF structure, checksums, metadata schema, tool/nozzle assumptions, plate bounds, and compatibility with the selected X2D/H2D print mode.
4. **Map materials** — read real AMS/external-spool state from the target printer and require an explicit mapping for every used filament. Never synthesize tray IDs, colors, or availability.
5. **Gate printer state** — require a reachable, authenticated, idle, compatible printer; confirm model, firmware support, build plate/nozzle assumptions, and sufficient storage.
6. **Upload** — transfer over an authenticated bridge or a currently supported Bambu integration path, with retry limits, checksum confirmation, and no secrets in browser logs.
7. **Start** — require a final user confirmation tied to the exact package checksum and target printer. Start only after upload and state confirmation.
8. **Observe** — verify the printer acknowledged the same project and surface any error without claiming success prematurely.

## LEVO Bridge requirements

- Local-only by default; explicit interface binding and origin allowlist.
- Strong request authentication and CSRF/replay protection.
- Encrypted credential storage outside the browser.
- Strict JSON/schema validation and bounded file sizes.
- Printer identity pinning, timeouts, rate limits, and idempotency keys.
- Redacted structured logs and an auditable action trail.
- Compatibility adapters isolated by printer model/firmware generation.

## Mobile bridge milestone

The repository contains a shared Capacitor 8 app for iOS and Android plus a versioned `LevoPrinter` contract. The web/native boundary supports capability negotiation and a sequential 192 KiB transfer protocol with declared-size bounds, per-asset SHA-256 validation, cancellation, and native cache cleanup. Android 1.2.1 advertises authenticated discovery, MQTT telemetry, FTPS transfer, and the printer's Developer Mode raw-G-code command as a distinct `rawGcodePrintJob` capability. It pins both transport certificates, keeps the access code in memory, requires an idle printer and a final checksum-bound user confirmation, and requires a matching MQTT acknowledgement (or live transition out of idle after an acknowledgement timeout). iOS continues to advertise those adapters as unavailable.

The Android bridge deliberately reports `packagePrintJob: false`: raw `.gcode` is not presented as a Bambu `.gcode.3mf` package. Physical X2D/H2D firmware verification remains outstanding, so this LAN path is marked experimental rather than certified.

## Evidence required before enabling

- Bambu Lab partner approval, official technical documentation, and issued authorization credentials for the **cloud** route (`devpartner@bambulab.com`).
- Explicit LAN Only/Developer Mode enrollment for the **local** route; no cloud account credentials are accepted by this route.

- Golden package fixtures accepted by Bambu Studio/Connect without mutation.
- Negative tests for corrupt metadata, wrong model, wrong nozzle, overflow, and unsafe AMS mapping.
- Integration tests on real X2D and H2D hardware in each supported nozzle mode.
- Verified upload, start, cancellation, reconnect, and error-state behavior.
- A documented firmware/authorization compatibility matrix.

Until all package gates pass, the app must not advertise `.gcode.3mf` packaging. The experimental Android raw-G-code route may run only after authenticated live status, encrypted file-transfer verification, an idle-state check, and explicit final confirmation. The website's primary path is the «تجهيز لـ MakerWorld» prepare-and-handoff flow above; real G-code preview/download/share, USB handoff, and Bambu Connect/Studio remain available as secondary actions, and the phone-only private MakerWorld → Bambu Handy flow is unchanged.
